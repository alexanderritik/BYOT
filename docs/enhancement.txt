    2. Don't use strings.HasSuffix() for everything

    This is a more important routing issue.

    Currently:

    if strings.HasSuffix(path, "/runs") {

    means something like:

    /tests/foo/bar/runs

    could potentially be interpreted as a test ID of:

    foo/bar

    That's probably not what you want.

    You know your routes have a specific structure:

    /tests/{testID}
    /tests/{testID}/runs
    /tests/{testID}/config
    /tests/{testID}/schedule/start
    /tests/{testID}/schedule/stop

    You can parse the path into pieces.

    For example:

    parts := strings.Split(strings.Trim(path, "/"), "/")

    For:

    /tests/abc/runs

    you get:

    ["abc", "runs"]

    For:

    /tests/abc/schedule/stop

    you get:

    ["abc", "schedule", "stop"]

    Then routing becomes much more explicit.

    For example:

    parts := strings.Split(strings.Trim(path, "/"), "/")

    switch {
    case len(parts) == 1:
        // /tests/{id}

    case len(parts) == 2 && parts[1] == "runs":
        // /tests/{id}/runs

    case len(parts) == 2 && parts[1] == "config":
        // /tests/{id}/config

    case len(parts) == 3 &&
        parts[1] == "schedule" &&
        parts[2] == "start":
        // /tests/{id}/schedule/start

    case len(parts) == 3 &&
        parts[1] == "schedule" &&
        parts[2] == "stop":
        // /tests/{id}/schedule/stop
    }

    This is more verbose initially, but it makes the allowed URL structure much clearer.

    13. One important concurrency issue in your scheduler

    There's another improvement I would make after the above.

    Your scheduler does:

    due, err := s.tests.ListDueScheduled(ctx, now)

    Then for every test:

    s.fire(ctx, test, now)

    Inside fire():

    next, err := schedule.NextRun(...)

    then:

    UpdateNextRunAt(...)

    then:

    HasActiveJob(...)

    then:

    queue.Enqueue(...)

    There is a potential race if you ever run multiple scheduler instances.

    For example:

    Scheduler A                  Scheduler B

    ListDue → Test A             ListDue → Test A
         ↓                            ↓
    UpdateNextRunAt               UpdateNextRunAt
         ↓                            ↓
    HasActiveJob                  HasActiveJob
         ↓                            ↓
    Enqueue                       Enqueue

    Both could potentially enqueue the same scheduled test.

    If your application runs only one scheduler process, you're less exposed to this.

    But if you eventually run multiple replicas, you should make claiming a scheduled run atomic in PostgreSQL.

    That's a separate improvement I'd do later.
    14. One more thing: schedule/stop doesn't stop a currently running test

    This is important.

    Your:

    POST /tests/{id}/schedule/stop

    only does:

    schedule_enabled = false

    It does not cancel a currently running job.

    So:

    Test A scheduled
           ↓
    Job starts running
           ↓
    POST /tests/A/schedule/stop
           ↓
    Future schedules stop
           ↓
    Current job continues

    That's actually a reasonable design.

    Your other endpoint:

    POST /stop
    {
        "testId": "A"
    }

    is the one that actually stops active jobs:

    active, err := hl.queue.ListActiveForTest(...)

    and:

    runtime.Cancel(job.UUID)

    So you have two distinct concepts:

    /schedule/stop
        = don't create future scheduled jobs


    /stop
        = stop currently active jobs

    That distinction is good.
